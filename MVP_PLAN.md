# План инженерного MVP

Рабочее название: **Jev Launcher**. Платформа: Windows 10/11 x64. План составлен 2 октября 2026 года.

Сначала создаём работающую оболочку: каталог приложений, папок и файлов, понятные описания, поле ввода и открытие выбранного объекта. После этого подключаем decision models и проводим эксперименты. В текущем репозитории пока подготовлены план и настройки Git; приложение ещё не реализовано.

## 1. Что должно получиться

Пользователь вызывает небольшое окно, вводит текст, выбирает объект из списка и открывает его. Каталог собирается из доступных источников Windows; пользователь может добавлять объекты и править их описания.

Пример сценария:

1. При первом запуске приложение находит ярлыки и приложения из меню «Пуск».
2. Пользователь добавляет папку проекта и описывает её как «проект по машинному обучению».
3. По вводу «машинному обучению» обычный текстовый фильтр показывает эту папку.
4. Пользователь нажимает Enter, и папка открывается в Проводнике.
5. На отдельном этапе инженерной части готовая ASR-модель переводит речь в текст и заполняет то же поле ввода.

На этом этапе решение о запуске принимает пользователь. Свободные смысловые формулировки, опечатки и ошибки распознавания станут задачей последующих ML-экспериментов.

**В MVP входят:**

- автоматический сбор доступных приложений и явное обновление каталога;
- ручное добавление приложения, папки или файла;
- описания, альтернативные названия, избранное, включение и отключение объектов;
- обычный поиск по названию, альтернативным названиям и описанию;
- открытие выбранного объекта, сообщения об ошибках;
- интерфейс с управлением с клавиатуры, горячей клавишей и значком в трее;
- сохранение каталога и пользовательских изменений между запусками;
- подключение готового стороннего распознавания речи отдельным этапом.

**За пределами этого этапа:** decision models, генерация описаний через LLM, дообучение и сжатие моделей, сравнение ML-методов, управление окнами других приложений, выполнение произвольных команд, поиск по содержимому всех файлов, синхронизация и учётные записи.

## 2. Стек и устройство приложения

| Часть | Решение | Причина |
| --- | --- | --- |
| Основная логика | Python 3.12 | Удобно затем подключать ML-эксперименты |
| Интерфейс | PySide6 + Qt Quick/QML | Небольшое настольное окно с собственным оформлением |
| Каталог | SQLite через стандартную библиотеку | Локальное хранение без отдельного сервера |
| Импорт и запуск | API Windows, фиксированные системные вызовы | Используем зарегистрированные способы открытия объектов |
| Оформление | QML-компоненты и системные иконки | Единый дизайн и знакомые изображения приложений |
| Сборка | PyInstaller, сначала one-folder и windowed | Проще проверить ресурсы QML и работу на Windows |
| Проверки поведения | pytest при реализации | Проверяем каталог и маршрутизацию открытия |

Один процесс приложения. Сканирование, извлечение иконок и сетевое распознавание выполняются в фоновых задачах; интерфейс получает результаты через сигналы Qt. В MVP отдельный веб-сервер не нужен.

Версии зависимостей фиксируем при создании первого запускаемого приложения и проверяем сборкой. Сейчас не добавляем конфигурацию пакета или зависимости, которые ещё не использует код.

Основы выбранного UI доступны в [официальном примере PySide6/QML](https://doc.qt.io/qtforpython-6/examples/example_quick_window.html); варианты упаковки описаны в [документации Qt for Python](https://doc.qt.io/qtforpython-6/deployment/index.html).

## 3. Каталог объектов

### Сбор приложений

Первый набор источников:

1. Ярлыки .lnk из пользовательского и общего меню «Пуск». Сохраняем сам ярлык: он может содержать аргументы и рабочую папку.
2. Приложения с именами и AppUserModelID из Get-StartApps, в том числе приложения Microsoft Store. Системный список относится к текущему пользователю и не гарантирует обнаружение каждого portable-приложения: [документация Microsoft](https://learn.microsoft.com/en-us/powershell/module/startlayout/get-startapps?view=windowsserver2025-ps).
3. Объекты, явно добавленные пользователем через диалог выбора файла или папки.

Portable-программы можно добавить вручную. Реестр установленных программ при необходимости используем для дополнительных метаданных; запись об установке сама по себе не является способом запуска. UninstallString не используем для открытия.

Не сканируем все диски на наличие исполняемых файлов. Показываем источники и время обновления, чтобы было понятно, что найдено.

При обновлении:

- новые объекты добавляются, прежние сохраняют object_id;
- пользовательские описания, альтернативные названия и избранное сохраняются;
- исчезнувшие цели отмечаются как недоступные;
- сбой одного источника не удаляет записи из него и не мешает загрузить остальные;
- дубликаты сопоставляются по способу запуска и цели, с учётом аргументов и рабочей папки, а не только по отображаемому имени;
- разные профили или режимы запуска одного приложения могут оставаться отдельными объектами.

### Описания

У объекта есть название, тип, короткое описание и альтернативные названия. Пользователь может изменить их в каталоге.

Автоматически используем только доступные метаданные и небольшой проверенный справочник распространённых программ. Например: «редактор кода» для известного редактора. Для неизвестного приложения оставляем описание пустым и предлагаем заполнить его вручную.

У описания сохраняем происхождение: пользователь, справочник или метаданные. Описание папки и файла по умолчанию заполняет пользователь; содержимое личных файлов не читаем для его получения.

### Минимальная запись

| Поле | Смысл |
| --- | --- |
| object_id | Постоянный ID, независимый от отображаемого названия |
| kind | app, folder или file |
| name | Отображаемое название |
| description, description_source | Описание и его происхождение |
| aliases | Альтернативные названия, в том числе русские |
| launch_type | shortcut, executable, app_id, folder или file |
| launch_target | Путь к объекту либо зарегистрированный AppID |
| arguments, working_directory | Дополнительные сведения для запуска, если нужны |
| source, source_key | Источник и ключ для сопоставления при обновлении |
| enabled, available, favorite | Доступность и пользовательские настройки |
| last_seen, icon_key | Последнее обнаружение и ссылка на кеш иконки |

Каталог и настройки храним в %LOCALAPPDATA%/JevLauncher. Локальные пути, записи голоса и пользовательские данные не попадают в Git. В репозитории оставляем только вымышленные примеры.

## 4. Открытие и взаимодействие с программами

Весь запуск проходит через один вход: **открыть объект по object_id**. Приложение находит запись, проверяет её доступность и вызывает соответствующий способ открытия.

| Объект | Способ открытия |
| --- | --- |
| Ярлык .lnk | Windows Shell открывает сохранённый ярлык |
| Программа .exe | Запуск с отдельным списком аргументов и сохранённой рабочей папкой |
| Приложение с AppID | Зарегистрированный механизм активации Windows |
| Папка | Открытие в Проводнике через Windows Shell |
| Файл | Открытие в приложении, назначенном в Windows |

Для ярлыков, папок и документов подходит [os.startfile](https://docs.python.org/3/library/os.html#os.startfile). Для прямого запуска используем subprocess со списком аргументов и shell=False.

Текст из поля ввода не превращается в команду PowerShell или cmd. Будущая модель также выбирает известный ID, а исполняющая часть работает с сохранённой записью каталога.

Для внутренних вспомогательных процессов, например сбора системных метаданных, задаём [CREATE_NO_WINDOW](https://docs.python.org/3/library/subprocess.html#subprocess.CREATE_NO_WINDOW). Само приложение собираем без консольного окна. Пользовательская программа открывается обычным способом.

Ошибки показываем в интерфейсе: объект исчез, доступ запрещён, нет приложения для типа файла, активация не удалась. Успешная отправка команды открытия не означает, что целевая программа уже полностью загрузилась.

Взаимодействие в MVP ограничено открытием. Работа с меню и кнопками запущенной программы, закрытие процессов и переключение между уже открытыми окнами остаются последующим расширением.

## 5. Интерфейс и дизайн

### Главное окно

- Компактное изменяемое окно, ориентир для первого макета — 760 × 540 пикселей.
- Поле ввода получает фокус при открытии.
- Список результатов: иконка, название, короткое описание, тип объекта.
- Выбранная строка явно выделена. Enter открывает её; стрелки перемещают выбор.
- Esc скрывает окно, Ctrl+L возвращает фокус в поле.
- Есть доступ к каталогу и настройкам.
- Открытие происходит по явному выбору пользователя, без запуска при вводе текста.

Начальный фильтр игнорирует регистр и ищет подстроку в названии, альтернативных названиях и описании. Пустой ввод показывает избранное и доступный каталог. Если совпадений нет, показываем понятное пустое состояние.

### Каталог и настройки

В каталоге можно обновить список, добавить объект, изменить название и описание, задать альтернативные названия, включить или отключить запись, добавить её в избранное. Показываем источник и доступность.

В настройках оставляем только нужные пользователю функции: горячая клавиша, тема, настройка микрофона и распознавания после подключения голоса.

Приложение живёт в трее; меню содержит «Открыть» и «Выйти». Горячая клавиша по умолчанию — Ctrl+Alt+Space, с возможностью изменения. Используем [RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey) и показываем ошибку, если сочетание занято. Автозапуск Windows не включаем по умолчанию.

### Визуальные ориентиры

Нейтральная тёмная тема с одним умеренным акцентным цветом; системный шрифт Segoe UI; согласованные отступы с шагом 8 px. Используем настоящие иконки приложений, а при отсутствии — простую иконку типа объекта.

Проверяем читаемость, состояние фокуса, наведение, выбранную строку, масштабирование Windows и размер текста. Длинные названия не ломают список; полное название и путь доступны в деталях.

Отдельно оформляем первый запуск, сканирование, пустой каталог, отсутствие совпадений, недоступный объект и ошибку открытия. При частичном сбое сканирования найденные результаты остаются доступны.

## 6. Голос через готовую стороннюю модель

Первый вариант интеграции — Whisper Large V3 Turbo через Groq. Это готовая мультиязычная модель с API; бесплатный тариф имеет квоты, которые нужно проверить в аккаунте при реализации. Документация: [распознавание речи](https://console.groq.com/docs/speech-to-text), [лимиты](https://console.groq.com/docs/rate-limits).

Поток: кнопка записи → запись с микрофона → остановка → запрос распознавания → текст в общем поле ввода → выбор объекта пользователем.

Нужно предусмотреть:

- видимый индикатор записи, остановку и отмену;
- выбор устройства ввода и понятную ошибку доступа к микрофону;
- пустое распознавание, таймаут, отсутствие сети или API-ключа, превышение квоты;
- возможность исправить полученный текст;
- сохранение работоспособности текстового ввода при недоступном API.

Ключ храним вне Git. Записи по умолчанию не сохраняем; пользователь явно запускает отправку аудио стороннему сервису. Постоянного фонового прослушивания нет.

Собственную ASR-модель не обучаем. Если позже потребуется полностью локальный режим, отдельно проверим готовую модель через faster-whisper; два провайдера сразу не реализуем.

## 7. Подготовка к decision models

Инженерная часть должна позволить заменить обычный выбор объекта моделью, не переписывая каталог и запуск.

Будущей функции выбора передаём запрос и **полный включённый и доступный каталог**: object_id, название, тип, описание и альтернативные названия. Пути и команды остаются в локальной исполняющей части. Фильтр интерфейса не ограничивает список, который получит decision model.

Будущий результат: выбранный object_id либо необходимость уточнения/отсутствие подходящего объекта; вероятности сохраняем для экспериментов. Точный контракт уточняем при подключении первой модели. Сейчас не создаём пустую систему плагинов или заглушки моделей.

Экспериментальный запуск должен уметь оценивать выбор без открытия программ. Пользовательские клики можно позднее использовать для сбора примеров, но клик не считается автоматически правильной разметкой.

## 8. Структура при реализации

На текущем этапе в Git находятся документация и настройки репозитория. По мере появления кода создаём компактную структуру:

~~~
src/jev_launcher/
  app.py           # запуск приложения и соединение частей
  catalog.py       # SQLite, записи и пользовательские изменения
  discovery.py     # источники Windows и обновление
  launch.py        # открытие по object_id
  search.py        # обычный фильтр
  speech.py        # готовая ASR-интеграция, когда дойдём до голоса
  ui/
    Main.qml
    Catalog.qml
    Settings.qml
resources/         # оформление и проверенный справочник
tests/             # проверки существенного поведения
scripts/           # запуск и сборка, когда нужны
~~~

Дополнительные модули выделяем по реальной необходимости. Каталоги для ML-экспериментов создаём после готовности оболочки. Локальные модели, аудио, базы данных и результаты запусков игнорируются Git.

## 9. Этапы и критерии готовности

| Этап | Результат | Проверка готовности |
| --- | --- | --- |
| 0. Репозиторий и план | Markdown-план, README, настройки Git, первый коммит | Файлы сохранены; ветка main; рабочее дерево чистое |
| 1. Каркас окна | Запускаемый PySide6/QML-интерфейс с вымышленным каталогом | Ввод, выбор и состояния списка работают с клавиатуры |
| 2. Реальный каталог | Сбор Windows, SQLite, редактирование и ручное добавление | После обновления и перезапуска сохраняются ID и пользовательские поля |
| 3. Открытие объектов | Запуск всех поддержанных типов и обработка ошибок | Реально открываются обычное приложение, приложение с AppID, папка и файл |
| 4. Удобная оболочка | Итоговое оформление, иконки, горячая клавиша, трей | Проверены фокус, DPI, занятая горячая клавиша и отсутствие лишних консолей |
| 5. Голос | Готовая ASR заполняет поле ввода | Русская запись превращается в редактируемый текст; сбой API не мешает обычному вводу |
| 6. Сборка | Windows-сборка и инструкция запуска | Сборка запускается отдельно от среды разработки; повторно проверены каталог, открытие и голос |

Рабочую текстовую версию получаем после этапа 4. Инженерная версия с голосом готова после этапа 6. ML-эксперименты начинаем на проверенной оболочке.

## 10. Проверка и ограничения

Автоматические проверки добавляем вместе с поведением:

- объединение источников, различение одинаковых названий и разных параметров запуска;
- сохранение стабильных ID и пользовательских описаний при обновлении;
- корректное сохранение каталога, в том числе названий на русском;
- выбор способа открытия по типу объекта и обработка отсутствующей цели;
- отсутствие выполнения текста запроса как команды;
- отмена фоновых задач и защита от устаревшего результата распознавания.

Запуск внешних приложений в обычных тестах заменяем контролируемыми вызовами. Отдельно вручную проверяем реальные открытия на Windows: Блокнот или другое простое приложение, приложение с AppID, временную папку и документ с пробелами и кириллицей в названии. Проверяем удалённую цель и отсутствие файловой ассоциации.

На время медленного сканирования или распознавания окно должно оставаться отзывчивым. Ориентир для локальной фильтрации — до 100 мс на каталоге из 500 объектов; это цель для измерения, а не уже полученный результат.

Обнаружение не гарантирует полный список всех программ на компьютере. Доступность бесплатного ASR зависит от стороннего сервиса. Модульные проверки способа запуска не доказывают фактическое открытие окна — для этого нужна отдельная проверка готовой Windows-сборки.

**Готовность инженерного MVP:** реальный каталог с редактируемыми описаниями, сохранение состояния, удобный ввод и выбор, корректное открытие объектов, обработка ошибок, готовая ASR-интеграция и воспроизводимая сборка. Decision models подключаются следующим этапом.
