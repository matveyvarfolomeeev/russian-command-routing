# Launcher-v1: наборы для сравнения выбора объекта

Версия зафиксирована 3 октября 2026 года. Всего **400 авторских текстовых запросов**:
200 на реальном каталоге и 200 на полностью вымышленном. В каждом наборе
50 строк validation и 150 строк test. Train и аудио в этой версии отсутствуют.
Текущая редакция v1 — **только выбор одного однозначного объекта для открытия**;
неоднозначность, уточнения, отсутствующие объекты и отказы добавляются позже.

Для обычных запросов пользователя отдельно подготовлен
[launcher-basic-v1](../launcher-basic-v1/README.md) на тех же каталогах и целях.
Результаты базового и этого сложного наборов оцениваются отдельно.

## Расположение и состав

| Набор | Каталог данных | Происхождение каталога |
| --- | --- | --- |
| Реальный | `artifacts/benchmarks/launcher-v1/real` | Read-only снимок действующей базы; личные данные исключены из Git |
| Вымышленный | `data/benchmarks/launcher-v1/synthetic` | Все названия и назначения объектов придуманы для этого набора |

В обоих каталогах **177 объектов: 139 приложений, 20 папок и 18 файлов**.
Пути, аргументы запуска, иконки, избранное и ключи не включены. Метаданные
реального каталога сохранены как есть; содержание личных проектов не угадывалось.
У вымышленных объектов назначения задаются их описаниями.

В каждом наборе однозначные запросы охватывают **50 разных объектов**:
35 приложений, 10 папок и 5 файлов. На них приходится все 200 строк
(138 запросов к приложениям, 42 к папкам, 20 к файлам); остальные объекты
участвуют как отвлекающие варианты. Это выборка сценариев, а не равномерная
проверка всех 177 целей.

Распределение действий одинаково в каждом наборе:

| Действие | Validation | Test | Всего |
| --- | ---: | ---: | ---: |
| `open` | 50 | 150 | 200 |
| Всего | 50 | 150 | 200 |

В запросах есть названия, псевдонимы, описания назначения, разговорная речь,
опечатки, транслит, неправильная раскладка, отрицание отвлекающего варианта,
явная поправка выбора и смешение алфавитов. Сложность задают похожие объекты
и сочетание признаков: программа или справка, папка или приложение, обычный
или расширенный вариант, 32 или 64 бита, активный проект или его архив.
В test нет простых контрольных запросов только с точным названием;
такие контроли остаются в validation. Эмпирическая сложность ещё не измерена.
`tags` допускают несколько признаков; доли отдельных тегов у двух наборов
различаются. Для оценки качества группируйте результаты по тегам и каталогам.

## Контракт и правила ответов

Вход модели — только `query` и **полный список `catalog.objects`**.
В основной проверке используются все 177 вариантов, независимо от фильтра UI.
Эталонные ответы, `rationale`, теги, группы и ID примеров остаются у evaluator.

Задача — один запрос без истории диалога. Модель обязана выбрать ровно один
`object_id` из снимка; эталонное действие всегда `open`. Служебных вариантов
и порогов отказа в основной проверке нет. Программа открывает объект только
при обычной работе приложения; во время оценки вызов запуска не выполняется.

У каждого запроса одна положительная цель, обоснованная метаданными или
узнаваемым названием. Общий запрос «открой браузер» при нескольких браузерах
исключён: любимое приложение не подразумевается. «Не X, а Y» и явная поправка
«сначала хотел X, передумал — открой Y» требуют выбора Y и не являются отказом.
Запросы с несколькими положительными целями и продолжения диалога не включены.

Примеры из вымышленного test:

- «Нужна компактная читалка PDF без редактирования; не приложение для
  заполнения форм» → Страницезор.
- «Покажи активную папку сада с кодом и данными наблюдений, не старый архив»
  → Лунный сад.
- «Запусти обычную оболочку скриптомир на 32 бита, не вариант x64»
  → Скриптомир (x86).

## Файлы и происхождение разметки

В каждой директории лежат:

- `catalog.json`: существующий формат снимка, `schema_version: 1`, `catalog_hash`
  и список `objects`. Поля объекта: `object_id`, `name`, `kind`, `description`, `aliases`.
- `validation.jsonl`, `test.jsonl`: по одному JSON-объекту на строку, UTF-8, LF.
- `manifest.json`: ID версии, редакция `open-only`, происхождение каталога, счётчики, объявление проверки
  разметки и SHA-256 каждого файла. `catalog_hash` вычисляется по каноническому
  JSON списка объектов: `ensure_ascii=False`, `sort_keys=True`, разделители `,` и `:`.
  Порядок объектов входит в хеш.

Обязательные поля строки:

| Поле | Значение |
| --- | --- |
| `id` | Уникальный ID примера во всём комплекте |
| `query` | Текст, который получает модель |
| `expected_action` | Только `open` |
| `expected_object_id` | Единственный правильный ID из снимка; всегда заполнен |
| `input_type` | `text` |
| `group_id` | Связанный сценарий с его перефразами и искажениями |
| `tags` | Список признаков запроса и тип цели |
| `source` | `authored` |
| `rationale` | Обоснование ответа, недоступное оцениваемой модели |

В manifest зафиксированы `allowed_actions: ["open"]`,
`require_unique_target: true` и `metric: top1_accuracy`.

Все формулировки написаны Codex по каталогам и проверены вторым авторским
проходом по сериализованным строкам. Исправленные строки проверены повторно.
В manifest это отражено как `annotation_review.status: author_reviewed`,
`reviewed_rows: 200`, **`independent: false`**. Это авторские примеры, а не
реальные пользовательские логи или независимая человеческая разметка.
Предсказания сравниваемых моделей не использовались для назначения ответов.

## Разбиение и протокол сравнения

В каждом наборе 50 семейств сценариев: 13 в validation и 37 в test.
Перефразы и искажения одного сценария сохранены вместе. Соответствующие
семейства реального и вымышленного каталогов используют общий `group_id`
и одинаковое разбиение. Совпадающие запросы между каталогами также имеют
одну группу и разбиение; их ответы относятся к своему снимку.

На validation сравнивайте модели, промпты и настройки выбора объекта.
После фиксации настроек используйте test для итоговой проверки. Примеры
validation/test не включайте в будущий train. Новые данные, исправления
ответов или изменения каталога оформляйте новой версией с новыми хешами.

Качество реального и вымышленного наборов сообщайте отдельно.
Единственная основная метрика качества — **top-1 accuracy**:
число точно совпавших `object_id`, делённое на число всех запросов разбиения.
Уточнение, отказ, неизвестный ID, некорректный ответ или сбой считаются ошибкой;
не исключайте их из знаменателя и не учитывайте запасные кандидаты как успех.
Отдельно полезны результаты по тегам и типам объектов. Запишите версию набора,
хеш каталога, версию модели, настройки и порядок вариантов.
Во время измерения программы не открываются.

## Проверка целостности

Из корня репозитория:

~~~powershell
.\.venv\Scripts\python.exe scripts\validate_benchmark.py data\benchmarks\launcher-v1\synthetic
.\.venv\Scripts\python.exe scripts\validate_benchmark.py data\benchmarks\launcher-v1\synthetic artifacts\benchmarks\launcher-v1\real
~~~

Вторая команда дополнительно проверяет общие семьи между каталогами.
Валидатор использует стандартную библиотеку Python, читает только файлы набора
и выводит JSON-отчёт. Код возврата: 0 при успехе, 1 при ошибке данных.

Проверяются схема, обязательная единственная цель, действие только `open`, состав каталога,
хеши, объявление завершённой авторской проверки, разнообразие целей, дубли
и пересечения групп. Для дублей нормализуются регистр, пробелы, `ё/е`, NFKC
и конечные знаки `.?!…`. Проверка структуры не устанавливает смысловую
правильность ответа; её обеспечивает описанный авторский проход.

Локальный отчёт по обоим наборам и заметки проверки находятся в
`artifacts/benchmarks/launcher-v1/review.json`. Реальные данные и исходник
их подготовки не добавляются в Git. Для переноса вымышленного набора достаточно
четырёх файлов его директории и этого описания.
