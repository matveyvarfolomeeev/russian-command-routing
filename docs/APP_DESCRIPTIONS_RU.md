# Автоматические описания приложений: реализация и проверка

Historical experiment record. Paths under `artifacts/` refer to local files; published predictions and ledgers are in [public evidence](../results/README.md).

8 октября 2026 добавлено заполнение пустых описаний из ресурсов Windows и метаданных установленных пакетов WinGet. В реальном каталоге заполнены **12 карточек: 66 → 78 из 139 приложений**. Семь описаний получены из Windows, пять — из пакетов. Ручные описания, существующие карточки, названия, aliases, пути запуска и ID сохранены. Изменения применены к локальному каталогу; резервная копия и проверка чтением сохранены отдельно.

## Как собираются сведения

После обычного сканирования [сборщик](../src/jev_launcher/app_metadata.py) обрабатывает только приложения с пустым, не отредактированным вручную описанием.

1. Читает `FileDescription`, `ProductName`, `CompanyName` из version resources EXE, не запуская программу. Описания, просто повторяющие название, не добавляются. Метаданные EXE браузера не используются для ярлыков с `--app`/`--app-id`.
2. Получает список установленных package ID и версий через `winget export --source winget --include-versions`. Сам экспорт не устанавливает программы. Ищет пакет по точному имени карточки или имени продукта, проверяет package ID в установленном списке и читает описание именно установленной версии. Пакет Microsoft Store нельзя отождествлять с чужим одноимённым пакетом WinGet.
3. Использует пакетное описание, если сопоставление подтверждено; иначе — информативное описание Windows. Текст ограничен 400 символами. Английские и другие исходные описания не переводятся, языковая модель для генерации не вызывается.

Примеры: Anki 25.09, SharpKeys 3.9.4000, PyCharm Community 2023.3.5, Docker Desktop 4.92.0, SumatraPDF 3.6.1. Для Git Bash/CMD/GUI Windows сообщает одинаковое «Git for Windows»; такое обогащение не объясняет различия этих вариантов. Не все программы имеют полезные метаданные или доступный пакет нужной версии. **61 приложение осталось без описания.**

Публичные интерфейсы: [ресурсы версии Windows](https://learn.microsoft.com/en-us/windows/win32/api/winver/nf-winver-verqueryvaluew), [WinGet show](https://learn.microsoft.com/en-us/windows/package-manager/winget/show).

## Работа в приложении

Обогащение подключено к `scan_windows`, то есть к существующей кнопке обновления каталога и фоновому обновлению. Некэшированная работа WinGet ограничена 15 секундами на сканирование; общий скан также включает существующий Windows helper с отдельным timeout 45 секунд. Поиск и голосовая команда не обращаются за описаниями в сеть.

Кэш находится в `app-descriptions.json` рядом с локальной базой. Установленный список сохраняется на сутки; успешные описания — на неделю, подтверждённые отсутствия — на сутки. Ключи связаны с контрольной суммой установленного списка и версий. Сетевые ошибки не считаются постоянным отсутствием пакета. Повреждённый кэш можно восстановить при следующем сканировании. В этой Windows-среде атомарное переименование в зашифрованной папке профиля возвращало WinError 17; для восстанавливаемого кэша используется обычная запись.

В каталоге хранится происхождение: `windows_metadata` или `winget:<package_id>`. Обогащение сохраняет существующие содержательные описания и не понижает пакетное описание до запасного Windows-описания. Применение готовых описаний защищено транзакцией; повторно проверяются пустота поля и ручной override.

Основная модель и веса не переключены: приложение использует исходную E5 → Laya FP32 шага 568. Дообученная E5 ниже проверяется отдельно. После изменения текста карточек индекс пересчитывается по существующему hash карточек; исходный и обученный encoder имеют отдельные индексы.

## Проверка на прежнем реальном наборе

Те же 177 объектов и 150 уже известных validation-запросов: по 50 basic/difficult/STT. Запросы, targets, группы и исходные benchmark-файлы сохранены. Изменены только пустые описания 12 приложений. Сборщик не получает запросы или labels. Вымышленные каталоги и старый sealed test не открывались для нового выбора; обучения и выбора checkpoint нет.

| Модель | Basic /50 до → после | Difficult /50 | Старый STT /50 | Всего /150 |
| --- | ---: | ---: | ---: | ---: |
| Исходная E5 | 36 → 36 | 30 → 30 | 26 → 26 | 92 → 92 |
| Дообученная E5, шаг 142 | 45 → 47 | 39 → 39 | **39 → 40** | **123 → 126** |
| Исходная E5 → Laya FP32 | 42 → 44 | 38 → 39 | **35 → 34** | **115 → 117** |

У обеих E5 исходные top-1 на 150 строках совпали с предыдущими сохранёнными ONNX-результатами. Laya получает детерминированное перемешивание кандидатов из приложения; оно отличается от прежнего canonical shortlist порядка. Поэтому её baseline в этой проверке вычислен заново, а не взят из старой таблицы.

Дообученная E5 исправила три ошибки, не добавив новых. Все три относятся к файлу Git Release Notes: новые описания Git GUI/Bash/CMD помогли отличить приложение от документа с историей выпусков. Laya исправила пять ошибок и добавила три. Recall@20 исходной E5 остался 139/150, обученной — 142/150, но множества shortlist изменились у 127 и 96 запросов соответственно.

**Ни один из этих 150 запросов не нацелен на обогащённые 12 карточек.** Это проверка влияния обновлённых приложений как конкурирующих кандидатов, а не непосредственная проверка открытия новых описанных приложений.

## Отдельные запросы к двенадцати приложениям

Для каждого приложения добавлены два ручных запроса: по названию и по назначению, всего 24. Формулировки составлены после сбора описаний; некоторые содержат необходимые уточнения, например JetBrains, Bash или старый проигрыватель. Это **авторская диагностика**, не слепой набор и не STT. Она не использована для обучения, выбора весов или настройки описаний по ответам моделей.

| Модель | По названию /12 | По назначению /12 | Всего /24 | Цель в top20 /24 |
| --- | ---: | ---: | ---: | ---: |
| Исходная E5 | 12 → 10 | 8 → 8 | 20 → 18 | 23 → 21 |
| Дообученная E5 | 12 → 12 | **9 → 10** | **21 → 22** | **23 → 24** |
| Исходная E5 → Laya | 12 → 12 | 8 → 7 | 20 → 19 | 23 → 21 |

Обученная E5 стала правильно находить SharpKeys по переназначению клавиш через реестр. Исходная E5 стала путать явное Anki с Antigravity, а SharpKeys — с SharpKeys FAQ. Для запроса к читалке PDF/DjVu SumatraPDF оставалась в исходном top20 до и после обогащения, но Laya потеряла правильный выбор и ответила «Очистка диска». Это ошибка выбора при доступной цели. Это наблюдаемые изменения; отдельно вклад языка, длины, формулировки описания и состава конкурентов не измерен.

Уточнение 8 октября при последующей парной проверке E5 → Laya: прежнее объяснение ошибочно связывало регрессию SumatraPDF с пропажей цели из shortlist. Сохранённые прогнозы подтверждают её наличие в обоих вариантах; численные counts и прогнозы не изменены. [Новая проверка](E5_LAYA_PIPELINE_RU.md).

**Автоматическое описание не гарантирует улучшение.** Надёжный источник всё равно может дать слишком общий или многословный текст. На этих данных обученная E5 выиграла, а старый retrieval и следующая Laya получили смешанный результат. По 24 ручным примерам нельзя заявлять универсальное превосходство.

## Задержка

Один последовательный прогон тех же 150 запросов, после загрузки и подготовки каждого индекса. CPU i7-13700H, 6 быстрых ядер, E5 ORT 4 потока без spinning, Laya Torch FP32 6 потоков. Таймер включает свежий запрос, ранжирование, а для Laya — формирование карточек и выбор. STT, загрузка, первоначальное индексирование, сетевой сбор описаний и запись артефактов исключены.

| Модель | Медиана до → после | p95 до → после | Максимум до → после |
| --- | ---: | ---: | ---: |
| Исходная E5 | 6,02 → 6,48 мс | 7,94 → 8,18 мс | 9,93 → 9,75 мс |
| Дообученная E5 | 5,94 → 5,54 мс | 7,57 → 7,27 мс | 9,81 → 8,63 мс |
| Исходная E5 → Laya | 309,76 → 363,32 мс | 434,63 → 551,00 мс | 556,65 → 675,21 мс |

Эта короткая проверка на реальном каталоге не заменяет прежние independent400×2 timings. Различаются запросы и длины карточек; утверждения, что модель в целом ускорилась или стабильно укладывается в 500 мс, здесь нет. Более длинные карточки увеличивают объём работы Laya; E5 кодирует их при подготовке индекса.

## Проверки и первичные файлы

72 проверки сборщика, discovery и каталога прошли. После добавления транзакции — 48 проверок сборщика/каталога и выбранных GUI-сценариев; Ruff прошёл. Независимый пересчёт проверил **1044 прогноза**, counts, пары исправлений/регрессий, порядок по оценкам, softmax, quantiles, контрольные суммы, сохранение ID/aliases/файлов/папок и соответствие package ID/версий.

- Исходные и новые карточки, manifest (`artifacts/benchmarks/app-metadata-v2/manifest.json`).
- 12 описаний с происхождением (`artifacts/benchmarks/app-metadata-v2/description-updates.json`).
- Прежние 150: comparison (`artifacts/benchmarks/app-metadata-v2/evaluation-v2/comparison.json`).
- Новые 24: comparison (`artifacts/benchmarks/app-metadata-v2/diagnostic-evaluation/comparison.json`).
- Аудит (`artifacts/benchmarks/app-metadata-v2/audit.json`).
- Чтение после применения к приложению (`artifacts/benchmarks/app-metadata-v2/application-readback.json`).
- [Сбор и подготовка](../scripts/prepare_app_metadata_evaluation.py), [диагностические запросы](../scripts/prepare_app_metadata_diagnostic.py), [оценка](../scripts/evaluate_app_metadata.py), [пересчёт](../scripts/audit_app_metadata.py).

Первичный `app-metadata-v1` сохранён как предварительный сбор по одному точному имени; он содержал неподтверждённые совпадения и не применялся к каталогу. Первая оценка v2 остановилась из-за неверного пути к tokenizer; завершённые сравнения находятся в `evaluation-v2` и `diagnostic-evaluation`. Точная версия кода первого завершённого сравнения сохранена рядом с ним, поскольку затем оценщик расширен поддержкой 24 диагностических запросов.

Архив v3 остаётся прежним снимком 22 этапов. Новый опыт и прежняя metadata ablation записаны в текущем реестре отдельно; персональные SQLite-резервные копии не включаются в архив доказательств.
