# План экспериментов: модели, приоритеты и дообучение

Historical experiment record. Paths under `artifacts/` refer to local files; published predictions and ledgers are in [public evidence](../results/README.md).

Актуальность источников: **3 октября 2026 года**. Модели ещё не запускались на нашей задаче, их качество не измерено. Уже работают каталог, экспорт и простой фильтр; подготовлены датасеты [launcher-v1](../data/benchmarks/launcher-v1/README.md).

Добавлен отдельный [launcher-basic-v1](../data/benchmarks/launcher-basic-v1/README.md): ещё 400 обычных запросов, по 200 на тех же каталогах, 50 validation и 150 test. Семейства, цели и разбиения согласованы с launcher-v1. В первом сравнении измеряем top-1 accuracy отдельно на базовом и сложном профилях; базовый не заменяет проверку трудных, но встречающихся запросов. Совпадения фраз отмечены в manifest и не считаются независимым подтверждением.

4 октября подготовлен [launcher-train-v1](../data/training/launcher-train-v1/README.md): 5 664 синтетические обучающие строки, 708 исходных запросов, восемь отдельных каталогов по 177 объектов. Существующие validation/test сохранены и исключены из обучения вместе с целевыми объектами. Есть воспроизводимый общий формат и экспорт `choice + label` для Kev. Это подготовка данных; checkpoint ещё не обучался.

Добавлен голосовой профиль [launcher-asr-v1](../data/benchmarks/launcher-asr-v1/README.md): 400 исходных базовых фраз озвучены Windows TTS, искажены четырьмя условиями шума и пропущены через реальный Groq `whisper-large-v3-turbo`. В каждом каталоге сохранены 50 validation / 150 test, исходные цели и необработанные расшифровки. По авторской оценке 12 фраз потеряли различающий смысл, 29 спорны; они остаются в общей точности голосового пути. Это синтетическая речь; живые человеческие записи будут отдельной версией.

Для обучения устойчивости к текстовым ошибкам отдельно создан [launcher-stt-train-v1](../data/training/launcher-stt-train-v1/README.md): 16 992 искусственно искажённых запроса из исходного train, с 12 типами операторов и сохранением целевых ID. Существующая ASR-оценка используется только для проверки отсутствия пересечений. Искажения не являются измеренной частотой ошибок провайдера; модели ещё не обучались.

Цель — сравнить выбор программы, папки или файла по свободному русскому запросу, затем обучить компактную модель на найденных трудностях. Основной эксперимент передаёт **весь каталог**, как задумано в проекте. Поиск нескольких кандидатов перед decision model будет отдельным вариантом для сравнения.

## Исходные условия

При проверке рабочей базы: 177 доступных объектов, описания у 93, альтернативные названия у 31. Экспортируемые поля занимают около 28 тысяч символов JSON; это **не замер токенов**. Перед каждым запуском проверяем бюджет конкретного токенизатора, полноту вариантов и отсутствие обрезания.

Текущий ПК: 16 ГБ RAM, Intel Iris Xe. Для первого раунда большие модели используем через API; локальные CPU эксперименты начинаем с текстовых методов и небольшого encoder. Это выбор порядка работы, а не подтверждение совместимости всех открытых моделей с этим ПК.

**P0** — подготовка измерений; **P1** — обязательный первый раунд; **P2** — расширение сравнения; **P3** — дополнительные исследования после первых результатов. Оценка сложности ниже относится к подключению, а не к гарантированному сроку.

Для Kev автор рекомендует начинать с 4B и использовать 0.8B, когда важнее размер. Фиксируем ревизию весов, dtype и встроенную температуру: разные версии и настройки не должны оказаться одной строкой результатов. [Репозиторий Kev](https://github.com/jaredpalmer/kev).

Для E5 следуем формату автора: `query: ` перед запросом и `passage: ` перед описанием объекта, в том числе на русском. Ограничение 512 токенов относится к отдельному тексту, а не к общему количеству объектов: embeddings объектов считаются отдельно и кешируются. [Карточка E5](https://huggingface.co/intfloat/multilingual-e5-small/raw/main/README.md).

### Почему Laya отдельно

Карточка Laya Multilingual рекомендует около 20 вариантов в `choice`: вопрос и варианты делят фиксированный бюджет головы в 256 токенов. Увеличение `max_len` для длинного контекста само по себе этот бюджет не снимает. Автор также отмечает слабый zero-shot результат на части typed задач и избыточную уверенность. Поэтому прежнюю идею сделать её первым универсальным выборщиком из 177 объектов нужно пересмотреть. [Карточка модели](https://huggingface.co/convaiinnovations/laya-multilingual).

Для D06 сравниваем:

- **Все объекты попарно:** для каждого объекта двухвариантный `choice` «соответствует запросу / не соответствует», затем ранжирование всех 177 результатов. Это наш алгоритм поверх модели, а не один совместный выбор; измеряем общую задержку. Независимые оценки нельзя выдавать за распределение вероятностей по всему каталогу.
- **E5 → до 15 кандидатов → Laya:** отдельный эксперимент с предварительным поиском. В v1 предлагаем только ID объектов и измеряем recall предварительного поиска. Это сравнение другой архитектуры, а не замена основного режима.

В обоих случаях сохраняем все варианты, которые реально увидела модель, и проверяем обрезание.

## Что подготовить перед первым сравнением

1. Для launcher-v1 использовать сохранённые снимки как есть. Описания реальной базы не изменялись; содержание личных проектов не угадывалось. Улучшенные метаданные оформлять новым снимком и версией набора.
2. Сначала 30–50 ручных проверочных запросов: формат, полный список вариантов, ошибки API и токенизация. Эти запросы относятся к разработке, а не к итоговому тесту.
3. **Готово: 400 авторских текстовых запросов**, 200 на реальном и 200 на полностью вымышленном каталогах. В каждом наборе 50 validation и 150 test. Семейства перефразов и соответствующие сценарии двух каталогов сохраняются в одном разбиении. Проверка разметки выполнена автором; независимой человеческой проверки пока нет.
4. В launcher-v1 есть названия, опечатки, описания назначения, транслит, неправильная раскладка, папки и файлы. Сложные запросы объединяют несколько признаков и явно отличают цель от похожих объектов. «Не X, а Y» и поправка «сначала X — нет, открой Y» задают одну положительную цель Y. Неоднозначность, отсутствующие объекты, отмены и запреты открытия отложены до отдельного набора. Настоящие ASR-ответы на шумное TTS-аудио готовы в launcher-asr-v1; человеческое аудио добавляется позже.
5. Для будущего обучения отдельно отложить часть целевых объектов, не показывая их в train. Появление их метаданных в каталоге на тесте разрешено и является частью задачи.

Качество двух каталогов считать отдельно: в каждом только 150 test строк и несколько перефразов на сценарий. Это первоначальная оценка; редкую частоту ошибок, например ниже 1%, такой объём убедительно не подтверждает. Train-набор теперь создан отдельно как launcher-train-v1; существующие validation/test не использовать для обучения.

Основной ответ launcher-v1 — ровно один `object_id` из снимка, соответствующий `open(object_id)`. У каждого запроса единственная обоснованная цель. Неоднозначные запросы исключены, любимое приложение не подразумевается. Возвращённое уточнение, отказ или неизвестный ID считается ошибкой выбора; программы в процессе оценки не открываем.

## Метрики и журнал

| Измерение | Что записывать |
| --- | --- |
| Top-1 accuracy — основная и единственная метрика качества v1 | Число точно совпавших ID / все запросы данного разбиения; без исключения отказов, сбоев или неверных ID. Считать отдельно по каталогам, типам целей и тегам |
| Поиск кандидатов | Recall@k и итоговая top-1; пропущенная цель остаётся ошибкой всей системы |
| Производительность | p50/p95 полного запроса; отдельно холодная загрузка, подготовка каталога, модель и сеть |
| Ресурсы и цена | RAM/VRAM, входные токены, стоимость на 1 000 запросов, сбои/таймауты/повторы |
| Надёжность формата | Неизвестный ID, неполный список вероятностей, неверная схема, обрезанные кандидаты |

В launcher-v1 нет порогов отказа: метод всегда выбирает лучший объект. Confidence и scores можно сохранять для анализа, но они не меняют оценку точности. Сходство embeddings или fuzzy score не называем вероятностью без отдельной калибровки. `provider_confidence` сохраняем отдельно от максимума `probabilities`: семантика поля у провайдеров может различаться. Пороги, coverage и качество уточнений/отказов проверяем позже на отдельном наборе.

На один запуск сохраняем `catalog_hash`, hash набора/разбиения, model ID/revision, prompt version, режим полного/сокращённого каталога, dtype, seed/порядок вариантов и raw результат по каждой строке. Для локальных методов фиксируем машину; для API — измеряем сеть с нашего ПК. Условия хранения ответов и ограничения на использование API данных для обучения проверяем до distillation. Заявленные вендором миллисекунды не подставляем в наш журнал как измеренную задержку.

Первый раунд сравниваем на validation; после выбора кандидатов один раз читаем отложенный test. Последующие улучшения проверяем на новых подтверждающих примерах, чтобы тест постепенно не стал обучающим набором.

| Порядок | Эксперимент | Когда имеет смысл |

| 1 | Пары запрос–объект для E5 и классического ML; перефразы, опечатки, hard negatives из похожих программ и папок | Когда понятны реальные ошибки и есть независимый test |
| 2 | Дообучить E5, попарную Laya либо Kev-4B | Выбрать 1–2 кандидата по сочетанию качества, памяти и скорости, а не обучать все модели сразу |
| 3 | Использовать проверенного учителя для разметки/мягких ответов; ученик E5/Laya/Kev-0.8B | Когда учитель действительно лучше на ручном тесте; его ответы проверять, не объявлять эталоном |
| 4 | Learning curve 500 → 2k → 10k, несколько seeds; сравнение с тем же checkpoint без обучения | Чтобы отделить пользу объёма данных от случайного удачного запуска |
| 5 | Квантование и, при необходимости, изменение головы/архитектуры | После успешного обучения; повторить замеры качества и калибровки |

Первая обучающая версия использует полностью вымышленные метаданные с происхождением каждой строки и исключением объектов оценки. 5 664 строки — подстановки 708 исходных запросов, а не независимые сценарии; проверка разметки авторская. Дополнительные 16 992 STT-строки — связанные искажения этих же фраз. Следующая версия может добавить реальные обучающие объекты и журналы запросов, сохранив отложенные объекты. При дополнительных разбиениях целиком откладывать group_id; общие команды открытия сами по себе не являются новыми сценариями. ASR-валидация содержит реальные ответы выбранной сторонней модели; текстовые STT-операторы обучения остаются отдельной искусственной имитацией. Ответы учителя, сомнительные случаи и ручная разметка хранятся раздельно.

В Kev-экспорте все 177 вариантов передаются целиком и переставляются для каждой строки. Проверка токенизатором Qwen3.5-4B-Base дала 10 889–11 169 токенов на полную строку; все 5 664 записи помещаются с `--max_state 16384`, стандартный контекст обучения слишком мал. Это проверка токенизации, а не замер GPU-памяти или качества модели. При изменении токенизатора и представления каталога пересчитать бюджет.

Полный STT-экспорт проверен тем же токенизатором: 10 887–11 171 токен, все 16 992 записи помещаются с `--max_state 16384`. У него отдельные SHA-256 и отчёт токенизации; чистый экспорт сохранён.

Следующий шаг реализации: отдельный offline evaluator и адаптеры B00/B01/B02 + Clef-flash/d1/Jev. Единый адаптер получает `query` и snapshot, возвращает выбранный ID, scores/probabilities, время и usage. Тяжёлые зависимости моделей устанавливаются в отдельное экспериментальное окружение; GUI и `launch.py` для измерений не нужны. Обучающие данные готовы; evaluator, адаптеры моделей и запуск обучения в основном checkout **ещё не реализуются**.

## Снимок каталога

Обновите каталог в приложении и заполните нужные описания. На время эксперимента экспортируйте полный набор:

~~~powershell
.\.venv\Scripts\jev-catalog.exe export --output artifacts\catalog-v1.json
~~~

Формат:

~~~json
{
  "schema_version": 1,
  "catalog_hash": "sha256 от канонического списка objects",
  "objects": [
    {
      "object_id": "постоянный ID",
      "name": "Редактор",
      "kind": "app",
      "description": "Редактор кода",
      "aliases": ["вскод"]
    }
  ]
}
~~~

Хеш учитывает ID, названия, описания, типы, альтернативные названия и состав каталога. Изменение этих полей меняет хеш. Одинаковый снимок позволяет сравнивать модели на одинаковых вариантах.

Экспорт не содержит путь запуска, аргументы, API-ключ или иконку. Названия и описания всё равно могут быть личными данными; снимки сохраняются в игнорируемом каталоге artifacts.

ID устойчив внутри каталога при обновлении. На другом компьютере или в заново созданной базе ID могут отличаться: переносите в эксперимент снимок, а не заново собирайте варианты для каждого метода.

## Работа без интерфейса

~~~python
from jev_launcher.catalog import Catalog
from jev_launcher.search import filter_catalog

catalog = Catalog()  # Или Catalog("artifacts/sandbox/catalog.sqlite3")
query = "редактор кода"

Набор не использован для обучения или отбора моделей; смысловой просмотр разметки авторский. Использование test для настройки лишает его роли свежего подтверждения следующего изменения.

## Граница эксперимента

Оценка модели в launcher-v1 возвращает один ID и при наличии scores/probabilities. Не вызывайте launch_by_id во время измерения качества. Проверяйте top-1 accuracy на фиксированной разметке; задержку, ресурсы и сбои записывайте как технические характеристики. Уточнения, отказы и их калибровка относятся к последующим тестам.

После эксперимента выбранный ID можно передать существующему launch.py. Пути и способы открытия остаются в инженерной части. Отдельный агент, сервер или система плагинов для этого не нужны.
