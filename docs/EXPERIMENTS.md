# План экспериментов: модели, приоритеты и дообучение

Актуальность источников: **3 октября 2026 года**. Это план: модели ещё не запускались на нашей задаче, их качество не измерено. Уже работают каталог, экспорт и простой фильтр.

Цель — сравнить выбор программы, папки или файла по свободному русскому запросу, затем обучить компактную модель на найденных трудностях. Основной эксперимент передаёт **весь каталог**, как задумано в проекте. Поиск нескольких кандидатов перед decision model будет отдельным вариантом для сравнения.

## Исходные условия

При проверке рабочей базы: 177 доступных объектов, описания у 93, альтернативные названия у 31. Экспортируемые поля занимают около 28 тысяч символов JSON; это **не замер токенов**. Перед каждым запуском проверяем бюджет конкретного токенизатора, полноту вариантов и отсутствие обрезания.

Текущий ПК: 16 ГБ RAM, Intel Iris Xe. Для первого раунда большие модели используем через API; локальные CPU эксперименты начинаем с текстовых методов и небольшого encoder. Это выбор порядка работы, а не подтверждение совместимости всех открытых моделей с этим ПК.

**P0** — подготовка измерений; **P1** — обязательный первый раунд; **P2** — расширение сравнения; **P3** — дополнительные исследования после первых результатов. Оценка сложности ниже относится к подключению, а не к гарантированному сроку.

## Какие методы тестировать

| --- | --- | --- | --- | --- | --- | --- |
| B00 | P1 | Текущий `filter_catalog` | CPU, весь каталог | Зафиксировать качество уже работающего поиска | Не требуется | Низкая |
| B01 | P1 | Fuzzy matching + символьный TF-IDF/cosine, как два отдельных метода | CPU, оценка всех объектов | Проверить, сколько опечаток и приблизительных названий решается без нейросети | TF-IDF обучает словарь на каталоге, без размеченных запросов | Низкая |
| B02 | P1 | [intfloat/multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small/raw/main/README.md) | CPU; заранее посчитать embeddings каждого объекта | Смысловой поиск: может ли небольшая embedding модель решить задачу | Contrastive fine-tuning на парах запрос–объект | Низкая–средняя |

| D03 | P1 | [Jev 1.13, `jev-1.13.0`](https://docs.typesafe.ai/models) | TypeSafe API; полный `choice` | Сравнение с исходной моделью, вокруг которой возникла идея | Пользовательский fine-tuning отсутствует | Низкая–средняя |

| B04 | P2, после train-набора | Logistic Regression / Linear SVM на признаках пары запрос–объект | CPU; оценка всех объектов | Обучаемый классический ML конкурент на тех же данных | Обучить веса лексических признаков; версии с embedding признаками считать отдельно | Низкая–средняя |
| G01 | P3 | [Qwen3.5-0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B), затем 4B при необходимости | Отдельный runtime; генерация ограниченного ID/JSON | Обычная небольшая LLM: проверить качество, задержку и корректность формата относительно decision моделей | LoRA / distillation | Средняя–высокая |
| D07 | P3 | [shenjunhao/OpenJev-4B](https://huggingface.co/shenjunhao/OpenJev-4B) | Внешний GPU; полный набор вариантов | Дополнительный открытый подход после основных кандидатов | Есть код SFT и REINFORCE-A; проверить русский на нашей задаче | Высокая |

Для Kev автор рекомендует начинать с 4B и использовать 0.8B, когда важнее размер. Фиксируем ревизию весов, dtype и встроенную температуру: разные версии и настройки не должны оказаться одной строкой результатов. [Репозиторий Kev](https://github.com/jaredpalmer/kev).

Для E5 следуем формату автора: `query: ` перед запросом и `passage: ` перед описанием объекта, в том числе на русском. Ограничение 512 токенов относится к отдельному тексту, а не к общему количеству объектов: embeddings объектов считаются отдельно и кешируются. [Карточка E5](https://huggingface.co/intfloat/multilingual-e5-small/raw/main/README.md).

### Почему Laya отдельно

Карточка Laya Multilingual рекомендует около 20 вариантов в `choice`: вопрос и варианты делят фиксированный бюджет головы в 256 токенов. Увеличение `max_len` для длинного контекста само по себе этот бюджет не снимает. Автор также отмечает слабый zero-shot результат на части typed задач и избыточную уверенность. Поэтому прежнюю идею сделать её первым универсальным выборщиком из 177 объектов нужно пересмотреть. [Карточка модели](https://huggingface.co/convaiinnovations/laya-multilingual).

Для D06 сравниваем:

- **Все объекты попарно:** для каждого объекта двухвариантный `choice` «соответствует запросу / не соответствует», затем ранжирование всех 177 результатов. Это наш алгоритм поверх модели, а не один совместный выбор; измеряем общую задержку. Независимые оценки нельзя выдавать за распределение вероятностей по всему каталогу.
- **E5 → до 15 кандидатов → Laya:** отдельный эксперимент с предварительным поиском. Оставляем запас для служебных вариантов и измеряем recall предварительного поиска. Это сравнение другой архитектуры, а не замена основного режима.

В обоих случаях сохраняем все варианты, которые реально увидела модель, и проверяем обрезание.

## Что подготовить перед первым сравнением

1. Проверить назначения хотя бы 20–30 часто используемых объектов. Для папок проектов нужны описания их содержания; «Папка проектов: NN» почти не объясняет назначение. Обновить метаданные один раз и дать одинаковый снимок всем методам.
2. Сначала 30–50 ручных проверочных запросов: формат, полный список вариантов, ошибки API и токенизация. Эти запросы относятся к разработке, а не к итоговому тесту.
3. Затем независимый ручной набор порядка **400 запросов**: ориентир 100 validation и 300 test. Перефразы одного исходного запроса, его аудио и ASR текст держать в одном разбиении. Test не использовать для выбора формулировки вопроса, порога или обучающих примеров.
4. Добавить названия, опечатки, описания назначения, транслит, настоящий ASR текст, папки, неоднозначность, отсутствующие объекты и отрицания. Пример «не открывай браузер» должен допускать `no_action`; «не Telegram, а Discord» проверяет другое поведение.
5. Для будущего обучения отдельно отложить часть целевых объектов, не показывая их в train. Появление их метаданных в каталоге на тесте разрешено и является частью задачи.

Это небольшой набор для измерения, а не массовая генерация обучающего датасета. Результаты на 300 test строках — первоначальная оценка; редкую частоту ошибок, например ниже 1%, такой объём убедительно не подтверждает.

Основной ответ эксперимента: `open(object_id)`, `clarify`, `not_found` или `no_action`. Неоднозначный запрос не размечаем произвольным любимым приложением. Программы в процессе оценки не открываем.

## Метрики и журнал

| Измерение | Что записывать |
| --- | --- |
| Top-1 | Правильный объект на однозначных запросах, где он присутствует |
| Поведение при отказе | Отдельные accuracy/F1 для `clarify`, `not_found`, `no_action` |
| Ошибочный выбор открытия | Число неверных `open` / все запросы; дополнительно неверные `open` / все предсказанные `open` |
| Coverage | Доля запросов, на которых метод выбирает `open`; сравнивать вместе с ошибками |
| Калибровка | Brier/NLL/ECE, когда есть вероятности; отдельно по числу вариантов и до/после настройки на validation |
| Поиск кандидатов | Recall@k и итоговая top-1; пропущенная цель остаётся ошибкой всей системы |
| Производительность | p50/p95 полного запроса; отдельно холодная загрузка, подготовка каталога, модель и сеть |
| Ресурсы и цена | RAM/VRAM, входные токены, стоимость на 1 000 запросов, сбои/таймауты/повторы |
| Надёжность формата | Неизвестный ID, неполный список вероятностей, неверная схема, обрезанные кандидаты |

Пороги отказа и разрыв между первым и вторым кандидатом выбираем на validation. Сходство embeddings или fuzzy score не называем вероятностью без отдельной калибровки. `provider_confidence` сохраняем отдельно от максимума `probabilities`: семантика поля у провайдеров может различаться.

На один запуск сохраняем `catalog_hash`, hash набора/разбиения, model ID/revision, prompt version, режим полного/сокращённого каталога, dtype, seed/порядок вариантов и raw результат по каждой строке. Для локальных методов фиксируем машину; для API — измеряем сеть с нашего ПК. Условия хранения ответов и ограничения на использование API данных для обучения проверяем до distillation. Заявленные вендором миллисекунды не подставляем в наш журнал как измеренную задержку.

Первый раунд сравниваем на validation; после выбора кандидатов один раз читаем отложенный test. Последующие улучшения проверяем на новых подтверждающих примерах, чтобы тест постепенно не стал обучающим набором.

## После первого раунда: данные, обучение, сжатие

| Порядок | Эксперимент | Когда имеет смысл |
| --- | --- | --- |
| 1 | Пары запрос–объект для E5 и классического ML; перефразы, опечатки, hard negatives из похожих программ и папок | Когда понятны реальные ошибки и есть независимый test |
| 2 | Дообучить E5, попарную Laya либо Kev-4B | Выбрать 1–2 кандидата по сочетанию качества, памяти и скорости, а не обучать все модели сразу |
| 3 | Использовать проверенного учителя для разметки/мягких ответов; ученик E5/Laya/Kev-0.8B | Когда учитель действительно лучше на ручном тесте; его ответы проверять, не объявлять эталоном |
| 4 | Learning curve 500 → 2k → 10k, несколько seeds; сравнение с тем же checkpoint без обучения | Чтобы отделить пользу объёма данных от случайного удачного запуска |
| 5 | Квантование и, при необходимости, изменение головы/архитектуры | После успешного обучения; повторить замеры качества и калибровки |

Генерируем train по реальным метаданным объектов с происхождением каждой строки. Не смешиваем семейства шаблонов между train/test; будущий ASR набор должен содержать реальные ошибки выбранной сторонней модели, а не только случайные замены букв. Ответы учителя, сомнительные случаи и ручная разметка хранятся раздельно.

Следующий шаг реализации: отдельный offline evaluator и адаптеры B00/B01/B02 + Clef-flash/d1/Jev. Единый адаптер получает `query` и snapshot, возвращает выбранное действие, ID, scores/probabilities, время и usage. Тяжёлые зависимости моделей устанавливаются в отдельное экспериментальное окружение; GUI и `launch.py` для измерений не нужны. В этом изменении evaluator, train-набор и адаптеры **ещё не реализуются**.

## Снимок каталога

Обновите каталог в приложении и заполните нужные описания. На время эксперимента экспортируйте полный набор:

~~~powershell
.\.venv\Scripts\jev-catalog.exe export --output artifacts\catalog-v1.json
~~~

Формат:

~~~json
{
  "schema_version": 1,
  "catalog_hash": "sha256 от канонического списка objects",
  "objects": [
    {
      "object_id": "постоянный ID",
      "name": "Редактор",
      "kind": "app",
      "description": "Редактор кода",
      "aliases": ["вскод"]
    }
  ]
}
~~~

Хеш учитывает ID, названия, описания, типы, альтернативные названия и состав каталога. Изменение этих полей меняет хеш. Одинаковый снимок позволяет сравнивать модели на одинаковых вариантах.

Экспорт не содержит путь запуска, аргументы, API-ключ или иконку. Названия и описания всё равно могут быть личными данными; снимки сохраняются в игнорируемом каталоге artifacts.

ID устойчив внутри каталога при обновлении. На другом компьютере или в заново созданной базе ID могут отличаться: переносите в эксперимент снимок, а не заново собирайте варианты для каждого метода.

## Работа без интерфейса

matches = filter_catalog(catalog.items(), query)

print("Вариантов для модели:", len(full_candidates))
print("Совпадения текстового фильтра:", [item.object_id for item in matches])
~~~

Код ничего не открывает. Будущей decision model передавайте full_candidates целиком, независимо от matches. Фильтр — инженерная база сравнения, которая не заявляет понимание свободного текста.

Для отдельного каталога:

~~~powershell
.\.venv\Scripts\jev-catalog.exe --db artifacts\sandbox\catalog.sqlite3 scan
.\.venv\Scripts\jev-catalog.exe --db artifacts\sandbox\catalog.sqlite3 add "D:\My Project"
.\.venv\Scripts\jev-catalog.exe --db artifacts\sandbox\catalog.sqlite3 search "project"
~~~

CLI поддерживает scan, list, export, search и add. Он не содержит команды автоматического открытия по результату поиска.

## Запросы и разметка

Сохраняйте запросы отдельно от снимка. Пример будущей строки разметки:

~~~json
{"query": "открой программу для кода", "expected_action": "open", "expected_object_id": "ID из снимка", "input_type": "text", "group_id": "editor-paraphrases"}
~~~

Для отсутствующего объекта и неоднозначного запроса используйте not_found и clarify; для отмены или запроса ничего не открывать — no_action. Нажатие пользователя не считается автоматически правильным ответом.

Держите вместе связанные перефразы, голосовой пример и его ASR-текст. Чистый текст и распознанный текст оценивайте отдельно. Зафиксируйте каталог, разметку и разбиение до сравнения моделей.

## Граница эксперимента

Оценка модели возвращает ID, вероятности или отказ от выбора. Не вызывайте launch_by_id во время измерения качества. Проверяйте точность выбора, ложные открытия, уточнения, задержку и калибровку на фиксированной разметке.

После эксперимента выбранный ID можно передать существующему launch.py. Пути и способы открытия остаются в инженерной части. Отдельный агент, сервер или система плагинов для этого не нужны.
